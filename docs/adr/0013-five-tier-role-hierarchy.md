# 0013: 五層角色權限模型

## 狀態
已接受

## 背景
原本沿用舊系統的角色設計（`super_admin`/`admin` 權限相同、機構管理者查看+審核自己機構），但使用者在確認 RLS 權限邊界時，重新定義了更細緻的角色分層，其中一個重要修正是：**審查合格與否的權限不屬於機構管理者，而是平台管理者**（連帶修正了 [0006](./0006-pass-requires-manager-confirmation.md)）。

## 決策
角色分為 5 層，權限範圍如下：

| 角色 | 可見範圍 | 權限 |
|---|---|---|
| **系統管理者** | 全部機構 | 最高權限；可管理其他管理者帳號（新增/編輯/停用/重設密碼），其餘權限同平台管理者 |
| **平台管理者** | 全部機構 | 可建立學員/題庫等檔案、批次匯入資料、**審查及格作答是否確認通過**（見 [0006](./0006-pass-requires-manager-confirmation.md)）、日常維運操作 |
| **管理者** | 全部機構 | **純查看**，可看所有機構的考測狀況與分析報表，**不能新增/修改/匯入任何資料，也沒有審查權限**——單純的全域檢視/監督角色 |
| **機構管理者** | 僅自己機構 | 可查看自己機構學員的考測結果與分析報表，**不能**看其他機構的資料，**沒有**審查合格與否的權限 |
| **學員** | 僅自己 | 登入作答、查看自己的歷次成績與應考提醒 |

其他規則：
- **登入方式統一**：所有角色一律用「帳號代碼」（工號或對應的管理者帳號代碼）登入，呼應 [0008](./0008-unified-account-code-login.md)，不因角色而有不同的登入方式
- **身分綁定**：角色是帳號建立當下就設定好、綁定在該帳號底下的固定屬性（非登入時動態選擇），要變更角色需要更高權限的管理者去修改該帳號設定
- 資料庫層的 RLS 政策需要對應這 5 層角色分別設計政策（尤其「全部機構可見」vs.「僅自己機構」vs.「僅自己」三種可見範圍），而非只有「管理者 vs 一般人」二元判斷

## 後果
- 比舊系統的兩層（super_admin/admin）+ 機構管理者的三分法更細，RLS 政策設計複雜度提高——每張資料表的政策都要考慮 5 種身分的可見範圍，不是簡單的「admin 看全部、其他人看自己」
- 「管理者」這個純查看角色是新增的，舊系統沒有對應角色，需要確認實際會由誰擔任、有沒有使用情境上的更多細節（例如是否為外部稽核/上級主管專用的唯讀視角）——**若後續設計報表介面時發現這個角色的實際使用情境不夠清楚，可能需要回頭再確認**
- 「平台管理者」身兼建檔匯入與審查兩種職責，工作量集中，需注意人數配置是否足夠（呼應 [0006](./0006-pass-requires-manager-confirmation.md) 的後果欄）
