# 0008: 全帳號類型統一以「帳號代碼」登入，Email 只作為聯絡資料

## 狀態
已接受

## 背景
承 [0007](./0007-edge-function-for-grading.md) 之後的下一個問題：Supabase Auth 原生設計是給 email 登入用的，但本系統各角色原本的登入方式並不統一：
- 學員：工號
- 後台管理者（`admin`/`super_admin`）：自訂帳號名稱（如 `admin`）
- 機構管理者：舊系統是用 email 登入（見舊 `models.py` 的 `InstitutionManager.email`）

## 決策
1. **所有角色一律以「帳號代碼」登入**（學員=工號、後台管理者=帳號名稱、機構管理者=新設計的帳號代碼），不論建檔或登入畫面，使用者輸入/看到的都是這個代碼，完全不碰 email 格式。
2. 建立帳號時，程式在背後自動把帳號代碼轉換成 Supabase Auth 要求的內部 email 格式（例如 `{代碼}@{角色}.internal`），呼叫 Supabase Auth 建立使用者。這個轉換**完全由程式處理**，管理者建檔、學員/管理者登入全程只需要輸入/看到帳號代碼本身。
3. **機構管理者的真實 email 改回歸為單純的聯絡資料欄位**（存在後端資料表，非 Supabase Auth 的登入身分），用途限定為到期通知等系統寄信對象；不再兼任登入帳號。

## 後果
- 三種角色的登入體驗一致，使用者（尤其是外籍學員）不需要理解「工號背後其實是個 email」這件事
- 建立機構管理者帳號時，表單需要同時收集「登入用帳號代碼」與「收信用真實 email」兩個欄位，是新增的資料需求（舊系統這兩者是同一個欄位）
- 帳號代碼的內部轉換格式（`{代碼}@{角色}.internal`）需要確保跨角色不會撞號（例如學員工號剛好跟某個後台管理者帳號代碼一樣時，因為 domain 不同不會衝突，仍需在設計時明確分域）
- 密碼重設等 Supabase Auth 原生機制，都是對著這個內部轉換後的 email 操作，不會意外寄信到真實信箱（因為那組 email 本來就是內部虛構的，不是真的可寄達地址）——**忘記密碼由管理者手動重設，而非讓使用者走 Supabase 內建的寄信重設信箱流程**，因為那組信箱本來就收不到信
