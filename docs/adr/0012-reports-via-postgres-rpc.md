# 0012: 分析報表運算交給 Postgres RPC/View，不在前端彙整

## 狀態
已接受

## 背景
舊系統的分析報表（學員分析／考題分析／考測結果分析／人力留任分析，含年度/半年/季時間軸篩選＋機構/國籍等次篩選）在 Flask 伺服器端用 SQL 查詢＋Python 彙整資料後產生頁面。2 代前端直連 Supabase，沒有伺服器端可以做這件事，有兩個可能做法：

- **選項 A**：報表查詢寫成 Postgres 資料庫函式（RPC）或 View，彙總運算在資料庫層完成，前端只拿彙總後的結果來畫圖表
- **選項 B**：前端把明細資料整批下載，在瀏覽器 JavaScript 裡自行彙整計算（類似參考專案 `sd762/-` 的 `ReportTable` 做法）

本系統屬於「稽核等級、長期保存」的資料（見舊 `PLANNING.md` 的需求彙整），資料量會隨時間持續累積。

## 決策
選擇**選項 A**：分析報表的彙總邏輯寫成 Postgres 資料庫函式（RPC）或 View，前端呼叫時只取得已經算好的彙總結果（例如某年度、某機構、某語言別的及格率、平均分），資料庫負責 GROUP BY 等彙總運算；前端 React 元件只負責呈現圖表與篩選條件的互動。

## 後果
- 資料量隨時間增加時，查詢效能不會隨前端要下載的明細資料量等比例變差，彙總在資料庫層一次算完
- 需要撰寫 SQL（資料庫函式/View），比起把邏輯全部寫在前端 JavaScript 多一種語言/技能需求，且日後報表邏輯異動需要改資料庫端而非只改前端程式碼
- 報表邏輯與 [0007](./0007-edge-function-for-grading.md) 的評分邏輯一樣，不是純前端能完成的部分，都算是「必要的後端例外」，但都是 Supabase 代管服務（資料庫函式/Edge Function），不影響「不需自架伺服器維運」的核心目標
- 篩選條件（年度/半年/季、機構、國籍等）若要保持彈性，RPC 函式的參數設計需要涵蓋這些維度，未來新增篩選維度時需要調整資料庫函式
