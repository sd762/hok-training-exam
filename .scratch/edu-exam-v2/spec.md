# 規格書：清福長照集團教育訓練測考系統（2代）

## Problem Statement

清福長照集團旗下機構（護理之家、法人館 1~3館、養護機構 14 個院所）的員工教育訓練測考，原本用第三方 SaaS「OnlineExamMaker」，額度卡關、多語言題目要重複建立、報表無法跨測驗彙整。第一代自建系統（Flask + Render）解決了這些問題，但用了 Render 免費方案的伺服器，容器休眠喚醒會清空資料庫（管理者密碼、學員名單、考試紀錄全部重置），要避免得付費升級。此外，第一代沒有防代考機制——測考時無法確認作答者是本人。

## Solution

用「純靜態前端（GitHub Pages）+ Supabase（Postgres/Auth/Storage/Edge Functions）」重建系統，徹底移除「伺服器」這個會休眠/清空資料的角色。同時新增鏡頭監考機制（防代考），並將五層角色權限、審查流程、抽題規則等重新設計得更嚴謹。品牌識別採用清福長照集團的深紅色（`#BB1B21` 系）+ 中性灰階，系統名稱為「清福長照集團教育訓練測考系統」。

## User Stories

### 帳號與登入
1. 作為學員，我想用工號登入，這樣我不需要記住額外的帳號格式
2. 作為機構管理者，我想用帳號代碼（而非 email）登入，這樣所有角色的登入體驗一致
3. 作為平台管理者，我想建立各角色帳號時只需輸入帳號代碼，系統自動處理底層 Supabase Auth 的 email 轉換，這樣我不需要理解技術細節
4. 作為系統管理者，我想管理其他管理者帳號（新增/停用/重設密碼），這樣可以維持帳號體系的秩序
5. 作為任何角色，我想在忘記密碼時由管理者手動重設（而非收系統寄的重設信），因為我的登入帳號背後是內部虛構信箱，收不到信

### 機構與人員管理
6. 作為平台管理者，我想在後台維護機構清單（新增/編輯/停用機構類別與機構名稱），這樣機構異動不需要等開發改程式碼
7. 作為平台管理者，我想批次匯入學員名冊（Excel），這樣可以快速建立大量學員資料
8. 作為平台管理者，我想編輯單一學員的資料（工號、姓名、語言、到職日、機構、部門等），這樣可以修正個別資料
9. 作為系統管理者/平台管理者，我想停用離職學員而非直接刪除，避免誤刪在職人員的歷史紀錄

### 題庫管理
10. 作為平台管理者，我想用 Excel 批次建立繁體中文題目，這樣建題效率高
11. 作為平台管理者，我想下載「翻譯範本」（帶入現有中文題目）、填好越南文/印尼文翻譯後上傳，這樣不用重新輸入題目結構
12. 作為平台管理者，我理解各語言題目數量不需要一致（中文題庫本來就會比外語題庫多），系統不會因為某語言題目較少而阻擋出題（只要達到最低抽題門檻）

### 學員測驗
13. 作為學員，我想看到自己目前受訓階段應考的測驗提醒，這樣不會錯過考試
14. 作為學員，我想在開始測驗前看到鏡頭監考的同意書，並清楚知道會被全程無預警擷取畫面，這樣我知情同意才開始
15. 作為學員，我想在測驗過程中鏡頭全程開啟（含手機前鏡頭），系統據此確認作答者身分
16. 作為學員，我想在人臉暫時離開畫面時看到提醒訊息並有機會回到鏡頭前，而不是直接被強制中止測驗，這樣不會因為環境因素被誤判
17. 作為學員，我想每次測驗都是從題庫隨機抽 25 題、每題 4 分（滿分100，80分及格），且同一輪 3 次機會內第 1/2 次盡量涵蓋不同題目、第 3 次重新隨機，這樣公平又不會每次都考一樣的題目
18. 作為學員，我想看到的題目順序與選項順序都是隨機打亂的，這樣不會被同批考生對答案
19. 作為學員，我想在連續 3 次未通過後知道要鎖定 7 天才能再考，並看到明確的解鎖時間
20. 作為學員，我想在多語言介面（繁中/越南文/印尼文）下操作整個測驗流程，包含錯誤訊息，這樣看得懂系統在說什麼

### 審查與紀錄
21. 作為平台管理者，我想在學員及格後收到通知，去查看監考證據（快照/疑似違規事件）確認作答者身分無誤，這樣才正式核可這次及格
22. 作為平台管理者，核對無誤後我想把狀態改為「已確認通過」並讓對應監考快照可以被清除，這樣不會佔用過多儲存空間
23. 作為平台管理者，發現有出入時我想把狀態改為「存疑保留」並保留證據，這樣可以進一步調查
24. 作為系統設計者，我需要「存疑保留」最終被判定不合格時不追溯扣考試機會（視為作廢重新計算），因為審查必然發生在作答之後、有時間落差
25. 作為系統設計者，我需要學員在「待核對」或「存疑保留」狀態下不能推進到下一受訓階段、也不會誤觸發下一階段的到期通知

### 通知
26. 作為機構管理者，我想在自己機構的學員即將到達受訓里程碑前 3 天收到通知，這樣可以安排排考
27. 作為系統管理者/平台管理者，我想在後台設定 SMTP 寄信資訊，這樣通知才能真正寄出
28. 作為系統設計者，我需要通知檢查每天執行 1 次即可（同一天檢查多次結果相同，因為有去重機制）
29. 作為系統設計者，我需要通知排程與 Supabase 保活合併成同一個 GitHub Actions 排程工作，簡化維運

### 報表與權限
30. 作為系統管理者/平台管理者/管理者，我想看到全部機構的考測狀況與分析報表（學員分析/考題分析/考測結果分析/人力留任分析），並能依年度/半年/季、機構、國籍等維度篩選
31. 作為機構管理者，我只想看到自己機構的考測結果與分析，看不到其他機構的資料
32. 作為「管理者」角色，我只能查看報表與考測狀況，不能新增/修改/匯入任何資料，也沒有審查權限——純粹是全域的檢視/監督角色
33. 作為系統設計者，我需要五層角色（系統管理者/平台管理者/管理者/機構管理者/學員）的資料可見範圍由資料庫 RLS 政策強制，而非只靠前端畫面隱藏

### 部署與維運
34. 作為系統管理者，我想整個系統維運成本是 US$0/月，不需要自己管理伺服器
35. 作為系統設計者，我需要 GitHub repo 設為 Public 才能使用免費的 GitHub Pages，同時確保 Supabase service role key 絕不出現在前端程式碼或 repo 裡
36. 作為系統設計者，我需要沿用現有的 Supabase 專案（帳號 2 個免費專案額度已被本系統與清福技術考稽核系統占用），但整個重新設計 schema

## Implementation Decisions

完整決策與理由記錄在專案 repo 的 `docs/adr/0001` 至 `0014`，此處僅摘要對應模組：

- **前端**：Vite + React + TypeScript，Tailwind CSS + shadcn/ui，部署到 GitHub Pages（Public repo）。品牌色：深紅 `rgb(187,27,33)`（品牌識別用，不用於及格/不及格狀態色）
- **後端**：無自架伺服器。資料庫/Auth/Storage 用 Supabase（沿用既有專案 `khkvqkbssngclojtxkuv`，重新設計 schema）；出題/評分邏輯與到期通知檢查用 Supabase Edge Function；報表彙總邏輯用 Postgres RPC/View
- **排程**：一個 GitHub Actions 排程工作（每天 1 次），呼叫「到期通知檢查」Edge Function，該呼叫本身即順便完成 Supabase 保活
- **資料模型**（對應舊系統 `models.py` 但整個重新設計）：機構清單改為資料表（非常數）；帳號統一以帳號代碼登入，內部轉換 email 供 Supabase Auth 使用；作答狀態改為多態（`不及格` / `pending_review` 待核對 / `confirmed_passed` 已確認通過 / `flagged` 存疑保留），而非舊系統的及格/不及格二元判定
- **抽題邏輯**：同一鎖定循環（3次/輪）內，第1次全題庫隨機抽25、第2次從扣除後剩餘題目抽25、第3次重新全題庫隨機抽25；題目顯示順序與選項順序個別打亂；正解位置鎖定在資料庫的「原始選項順序」上，透過每次作答產生的 `option_order` 對照表雙向轉換顯示位置與原始位置
- **監考**：前端用 MediaPipe（或同等瀏覽器內建人臉偵測）持續偵測；快照上傳 Supabase Storage 與該次作答綁定；人臉連續3秒未偵測到 → 畫面警示 + 記錄疑似違規事件（不自動中止/不自動扣考試機會）
- **審查流程**：只有及格作答需要審查，審查者是平台管理者（不是機構管理者）；核對無誤 → confirmed_passed（快照可刪）；有出入 → flagged（保留待查，最終不合格則作廢重算、不追溯扣考試機會）
- **角色權限**（五層，見 0013）：系統管理者 > 平台管理者 > 管理者(純查看全機構) > 機構管理者(僅自己機構、純查看) > 學員(僅自己)。全部用 RLS 政策強制，非前端邏輯把關

## Testing Decisions

- **Edge Function 業務邏輯**（出題快照、評分、抽題輪替規則、到期通知檢查）：以 Edge Function 為測試邊界，直接呼叫函式驗證輸入輸出，不需要啟動完整前端；正解永遠不應出現在「出題」回應內容中，這是必測項目
- **RLS 政策**：以「不同角色的 Supabase 測試使用者」為邊界，驗證機構管理者/管理者/學員各自能查到、查不到哪些資料列，尤其是監考快照與其他機構學員資料的隔離
- **前端關鍵流程**（測驗作答、審查佇列操作）：針對使用者行為做元件測試，只驗證外部可觀察行為（畫面上看到什麼、按鈕點了之後狀態變什麼），不測內部實作細節
- 舊系統沒有留下自動化測試可參考，這部分是全新建立

## Out of Scope

- 舊系統既有的正式員工名單/歷史考試紀錄遷移（使用者已確認學員資料不重要、不需要備份/遷移，只有題庫需要保留）
- 桌面應用程式包裝（清福技術考稽核系統有 PyInstaller 桌面版，本系統目前僅規劃網頁版）
- 合格證書自動產生（舊系統 Phase 5 已確認移除此需求，2代沿用不做）
- 「管理者」純查看角色的實際使用情境細節（例如是否給外部稽核/上級主管專用）——待後續視報表介面設計進度再確認
