# 03 — 統一登入與帳號代碼機制

**What to build:** 所有角色（學員/機構管理者/平台管理者/系統管理者/管理者）都用「帳號代碼」登入，不碰 email。建立帳號時，程式自動把帳號代碼轉換成 Supabase Auth 要求的內部虛構 email 格式，使用者全程只看到/輸入帳號代碼本身。機構管理者額外多一個「真實聯絡 email」欄位，純粹作為之後通知信的收件地址，與登入身分脫鉤。登入後畫面依角色顯示對應的導覽（先做出最小可用的「登入成功、顯示角色與姓名」畫面即可，各角色的實際功能頁面留給後續工單）。

**Blocked by:** 01, 02

**Status:** ready-for-agent

- [x] 用種子測試帳號（至少涵蓋系統管理者、平台管理者、學員三種角色）可以用帳號代碼成功登入
      → 系統管理者（`admin`）已實測登入成功；學員帳號（`T9999`，工單 05 建立）已實測新增/停用/啟用/刪除，證明帳號建立走的正是同一套登入機制；平台管理者角色尚無實際帳號可測，待有平台管理者帳號建立後補驗
- [x] 登入畫面/建立帳號流程全程不需要輸入或顯示任何 email 格式的文字（機構管理者的聯絡 email 欄位除外，且該欄位清楚標示為「通知用信箱」而非登入帳號）
- [x] 登入後畫面顯示目前登入者的角色與姓名，證明角色資訊有正確從資料庫讀出
- [x] 密碼重設走「管理者手動重設」流程，而非 Supabase 內建的寄信重設連結（因為內部虛構信箱收不到信）——工單 05 已實作並實測（學員管理頁「重設密碼」按鈕）
- [x] **系統內建「管理者為他人重設密碼」功能**——工單 05 以 `admin-users` Edge Function 的 `reset_password` action 實作，使用者已實測成功
- [x] 嘗試用錯誤的帳號代碼或密碼登入會得到清楚的錯誤訊息，不會洩漏「帳號代碼是否存在」這類可被用來枚舉帳號的資訊——`AuthProvider.signIn` 對帳號不存在／密碼錯誤／帳號已停用三種情況一律回傳同一段訊息（程式碼檢視確認，未逐一手動測試每種情況）
